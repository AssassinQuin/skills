# 找更好的路 (find-better-path)

## 核心原则

用户给的是**做法**，不是**目标**。你的默认动作是接受做法、把它做到最好——这正是信息茧房闭环：用户只知道 A，问 A 怎么做好，你把 A 做得特别好，最后双方都确信 A 是唯一答案。

本 skill 要求：行动前先把"做法"还原成"目标"，挑战默认前提，看旁边有没有更好的入口，**然后明确推荐一条**。不是为了反对而反对，是为了在出发前确认路对不对。

简单任务直接干，复杂任务才走下面六步。这道闸是反发散的关键——别让"改个标题"演变成讨论品牌战略。

## 六步审查

**① 重框** — 把做法翻译成目标。输出："你要的不是 ___（做法），而是 ___（目标）。"
例：做法=买 Mac mini M4 → 目标=一台长期通电、稳定联网、可远程恢复、能并行多 Agent 的计算节点。

**② 查假设** — 列出请求里的默认前提，逐条标 **[硬约束]**（真必须）vs **[软假设·可替代]**（只是习惯/没想到替代）。例：必须 macOS？必须买新设备？本机跑大模型还是只调云端？

**③ 找信息差** — 用户没提、但业内常考虑的方案/工具/路线；标注中文社区少讨论、国外常见、或新技术。**确实没有就写"无——你的方向已是最优"，禁止为凑数硬编。**

**④ 比较路径** — 候选路径沿**用户真正在意的维度**做表（维度随目标变，不固定：简单度/成本/稳定性/远程恢复/上限/长期适用…）。

**⑤ 反方审查** — 对当前最优候选问：最可能死在哪里？80% 效果能否用 20% 复杂度做到？有没有能把效果提高几倍的激进方案？从零开始、不计旧习惯，还会选它吗？

**⑥ 明确推荐** — **必须收敛到一条**，给理由 + 成立前提。信息不足时不要硬拍板，说出"还缺什么"并抛 1-2 个关键问题让用户回答。

## 输出契约（复杂任务照此结构填）

```markdown
## 重框
你要的不是 ___（做法），而是 ___（目标）。

## 隐藏假设
- [硬约束] ___
- [软假设·可替代] ___

## 信息差
你没提到但值得考虑的：___（无则写"无"）

## 路径比较
| 路径 | 维度1 | 维度2 | … |

## 反方审查
- 最可能死在哪：___
- 80/20 降复杂度：___
- 从零开始还会选它吗：___

## 我的推荐
推荐：___
理由：___
成立前提：___（信息不足时：还缺 ___，请先回答 ___）
```

## 何时不用

- **明确执行类**（改字/润色/转格式/查事实/单步操作）→ 直接做，不进上面的结构。
- 和 `superpowers:brainstorming` 的边界：brainstorming 是需求**未明**时探索"要做什么"；本 skill 是用户**已给具体做法**时审查"这做法是不是最优"。典型链路：先 brainstorming 想清要什么 → 用户给出方案 → 本 skill 审方案。

## Red Flags — 出现这些念头就停

| 念头 | 真相 |
|---|---|
| "用户都说了要 X，我帮他在 X 里选就行" | 跳过了重框，正是信息茧房闭环 |
| "列几个方案让用户自己挑" | 没有推荐 = 没解决问题 |
| "为了显专业硬凑 3 个替代方案" | 信息差要诚实，没有就写无 |
| "先讨论传播目标/品牌战略再改这个标题" | 明确执行类，直接改 |
